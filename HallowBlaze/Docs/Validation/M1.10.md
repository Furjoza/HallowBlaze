# M1.10 — stabilna plansza po `Continue`

## Zakres i decyzja

Plansza nie otrzymała osobnego snapshotu ani nowego pola DTO. Jej stabilna tożsamość jest wyprowadzana z danych już utrwalanych w `RunState`: `RunId`, `RunSeed`, `CurrentDay` oraz `WorldNodeId`. Dzięki temu istniejące poprawne save v1 pozostają obsługiwane bez migracji i bez resetu profilu lub runu.

Nowy run otrzymuje utrwalany, tekstowy GUID jako część `RunId`. Zastąpił on wcześniejsze generowanie identyfikatora z `UtcNow.Ticks`, aby board seed nie zależał pośrednio od zegara. Wczytane save v1 zachowują istniejące `RunId`; nie są przepisywane.

`Exit to Menu` nie zapisuje stanu środka planszy. Odłącza aktywny run od sesji, pozostawiając na dysku ostatnią zatwierdzoną granicę. Kolejne `Continue` odtwarza zasoby tej granicy, ten sam gameplayowy układ i tę samą pozycję startową.

## Reguła seeda

`RunState.GetBoardSeed()` oblicza 32-bitowy FNV-1a po następującej uporządkowanej zawartości:

1. domena `hallowblaze.board-layout.v1`;
2. `RunId`;
3. `RunSeed`;
4. `CurrentDay`;
5. `WorldNodeId`.

Teksty są kodowane jako UTF-8 poprzedzone 32-bitową długością, a liczby jako 32-bitowe wartości little-endian. Wersjonowana domena oddziela seed planszy od innych zastosowań RNG i pozwala w przyszłości jawnie wprowadzić nowy algorytm układu. Obliczenie nie zależy od `string.GetHashCode()`, czasu, `UnityEngine.Random.state`, kolejności `Instantiate` ani `InstanceID`.

Golden vector dla `run-001`, run seed `1729`, dnia `0` i węzła `forest.start` wynosi `-1283061345`.

## Rozdzielenie RNG

`BoardManager` tworzy lokalny `System.Random` z board seedem. Ten strumień steruje wolnymi pozycjami, liczbą obiektów, wyborem prefabów gameplayowych i dropem jedzenia ze ściany. `UnityEngine.Random` jest używany tylko do kosmetycznych wariantów podłogi i zewnętrznej ściany. Dźwięk, animacja ani inne kosmetyczne losowanie nie przesuwają strumienia gameplayowego.

## Dowód czerwony i korekty testów

- Przed dodaniem API board seeda build ujawnił `9` oczekiwanych błędów braku `GetBoardSeed`.
- Przed zmianą semantyki wyjścia skupiona macierz lifecycle miała wynik `12/15`; trzy porażki potwierdzały, że `ExitToMenu` nadal wykonywał zapis środka planszy.
- Pierwsze pełne EditMode miało wynik `87/88`, ponieważ golden vector dla dnia `0` używał w teście domyślnej konfiguracji dnia `1`. Jawne wejście `initialDay: 0` dało końcowe `88/88`.
- Pierwsze pełne PlayMode miało wynik `25/26`. Istniejący fixture pauzy nazywał scenariusz zachowaniem zapisanego runu, lecz tworzył run przed inicjalizacją persistence. Po ustawieniu fixture zgodnie z produkcyjną kolejnością skupiony test przeszedł `1/1`, a pełna macierz `26/26`.
- Pierwszy niezależny review wykazał, że włączenie `RunId` do board seeda nadało znaczenie wcześniejszemu generowaniu identyfikatora z `UtcNow.Ticks`. Zegar zastąpiono GUID. Po korekcie skupiona rekonstrukcja przeszła `1/1`, a pełna końcowa sekwencja PlayMode → EditMode przeszła `26/26` i `88/88`.

## Środowisko i ograniczenia

Unity uruchomione w batchmode konsekwentnie usuwało zaakceptowany symbol `SENTIS_ANALYTICS_ENABLED` z `ProjectSettings.asset`. Po każdym przebiegu przywrócono zatwierdzoną wartość `APP_UI_EDITOR_ONLY;SENTIS_ANALYTICS_ENABLED`; końcowy postflight nie wykazuje zmiany `ProjectSettings`.

Ręczna próba wielokrotnego `Continue` w interaktywnym buildzie lub Editorze: `Not run`. Automatyczny PlayMode pokrywa dwukrotne `Continue`, restart instancji `GameManager`, różne stany kosmetycznego RNG, identyczność układu, pozycję startową i rollback niezapisanych zasobów.
