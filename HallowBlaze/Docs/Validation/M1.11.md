# M1.11 — powrót do menu z ekranu porażki

## Baseline i zakres

- branch: `M1/LoseScreen`;
- baseline lokalnego `master`: `752187b4c97c9adb3782a6cc188856abf16d37a0`;
- schema save: bez zmian;
- persistence testów: unikalne katalogi pod `Path.GetTempPath()`, bez odczytu i zapisu prawdziwego profilu gracza.

Implementacja dodaje rozłączne akcje `Restart` i `Menu` do istniejącego widoku game over. Obie akcje używają jednej bramki dokładnie-raz, natychmiast wyłączają oba przyciski oraz przywracają `Time.timeScale` i blokadę inputu. `Menu` jest dostępne wyłącznie po pełnym sukcesie terminalizacji, sygnalizowanym przez odłączenie runu od sesji.

## Struktura widoku game over

```text
Canvas/Panel
├─ LevelImage
│  ├─ LevelText
│  └─ ScoreText
├─ RestartBttn
│  └─ RestartBttnText: "Restart"
└─ MenuBttn
   └─ MenuBttnText: "Menu"
```

| Kontrolka | Persistent callback | Pozycja | Nawigacja |
| --- | --- | --- | --- |
| `RestartBttn` | `RestartBttnScript.Restart` | `(-110, 20)` | w prawo do `MenuBttn` |
| `MenuBttn` | `RestartBttnScript.ReturnToMenu` | `(110, 20)` | w lewo do `RestartBttn` |

Obie kontrolki są ukrywane podczas `InitGame` i aktywowane razem po `GameOver`.

## Akcje i persistence

| Akcja / stan | Run w sesji | `profile.json` | `run.json` | Następna scena | Wynik |
| --- | --- | --- | --- | --- | --- |
| death zakończony poprawnie | odłączony | zachowany z jednym podsumowaniem `Dead` | usunięty | nadal `Main` | terminalizacja dokładnie raz |
| `Menu` po death | brak nowego runu | bez dodatkowego podsumowania | nadal brak | `Menu` | `Continue` nieinteraktywne |
| podwójne `Menu` | brak nowego runu | bez dodatkowego podsumowania | nadal brak | jedno żądanie `Menu` | drugie kliknięcie zablokowane |
| `Restart` po death | świeży aktywny run `100/100`, dzień `0` przed ładowaniem | profil zachowany | świeży run zapisany | `Main` | po inicjalizacji sceny dzień `1` |
| podwójny `Restart` | dokładnie jeden świeży run | profil zachowany | jeden świeży run | jedno żądanie `Main` | drugie kliknięcie zablokowane |
| błąd zapisu profilu podczas death | terminalny run pozostaje podpięty | zapis nieudany | poprzedni run zachowany | brak żądania `Menu` | przejście bezpiecznie zablokowane |

Po rzeczywistym przejściu `Main → Menu` ten sam `GameManager` pozostaje aktywny i zasubskrybowany do kolejnych zmian scen. `StartBttnScript` używa tego samego źródła katalogu persistence co `GameManager`, dzięki czemu stan `Continue` jest wyliczany z właściwego profilu i runu.

W każdym końcowym przebiegu: failed `0`, skipped `0`, inconclusive `0`.

Rzeczywisty test scenowy:

- ładuje `Main` i terminalizuje run przez produkcyjny `PlayerScript`;
- wywołuje serializowany `Button.onClick` kontrolki `MenuBttn`;
- potwierdza target `RestartBttnScript` i metodę `ReturnToMenu`;
- ładuje `Menu` i potwierdza `ContinueBttn.interactable == false`;
- sprawdza zachowany `profile.json`, brak `run.json` i pojedyncze podsumowanie `Dead`;
- skanuje wszystkie obiekty obu scen pod brakujące komponenty i `Missing Script`;
- potwierdza `Time.timeScale == 1`, odblokowany input oraz aktywny singleton `GameManager`.

Istniejący restart jest również wykonywany przez jego serializowany `Button.onClick` i odtwarza świeży run. Osobne testy z wstrzykniętym loaderem sceny potwierdzają blokadę drugiego kliknięcia dla obu akcji.
